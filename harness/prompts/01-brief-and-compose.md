# 1. 기획 해석(brief) → 2. 섹션 구성(compose)

## 1-1. 입력 읽기

| 입력 | 읽는 법 |
|---|---|
| 문서 URL (노션·구글독스·컨플루언스 등) | 연결된 커넥터가 있으면 그걸로, 없으면 사용자에게 본문 붙여넣기 요청. 하위 페이지가 기획 본문이면 한 단계 더 |
| 문서 첨부 (docx·pdf·md) | 파일 읽기 스킬로 텍스트 추출 |
| 자연어 한두 줄 | 그대로 brief 로 |
| 이미 lp-spec / 빌더 doc JSON | 필드를 lp-spec 으로 매핑만 (카피는 §3 규칙으로 다시 다듬기) |

## 1-2. brief 추출 (내부 메모, 사용자에게 길게 보여주지 않음)

```
purpose        : 서비스 소개 | 신청 유도 | 구매 전환 | 멤버십 구독 | 이벤트 참여 | 브랜드 인지도   (질문 Q1 선택지)
primaryAction  : 회원가입 | 견적 신청 | 앱 다운로드 | 문의하기 | 구독 …                         (Flow Q2)
target         : 누구에게 (1인 가구, 신혼, 가족, 사업장 …)
problem        : 타깃이 지금 겪는 불편 2–4개
promise        : 우리가 해결하는 방식 = USP 후보 (숫자·보장·조건은 원문 그대로 보존)
proof          : 후기·수치·파트너·보장 근거
flow           : 이용 절차
objections     : FAQ 후보 (가격, 환불, 소요시간, 조건 …)
related        : 함께 쓰면 좋은 서비스 (cross-sell)
tone           : 원문이 지정했으면 그대로, 없으면 오늘의집 기본 톤
seo            : 자동 생성 (목적+액션+brand) 또는 원문 값                                    (Flow Q3)
gaps           : 원문에 없는 것 → assumptions 로 기록
```

**사실은 원문에서만.** 금액·비율·기간·보장 한도·업체 수 같은 숫자는 원문에 있을 때만 쓴다.
없으면 숫자 없는 표현으로 쓰고 `assumptions` 에 "보상 한도 수치 확인 필요"처럼 남긴다. 후기는 원문에 없으면
"예시 후기"임을 `assumptions` 에 명시한다.

## 1-3. 질문은 최소로

목적·핵심 액션·타깃 중 **둘 이상이 원문에서 추론 불가**할 때만 AskUserQuestion 한 번(최대 3문항 — Q1 목적 6지선다 · Q2 핵심 액션 6지선다 · Q3 SEO 자동/직접).
그 외에는 가정하고 진행 → 시안에서 확인받는 편이 빠르다.

## 1-4. 타이틀 레이아웃 택1 (페이지당 하나)

| titleLayout | 모양 | 고르는 기준 |
|---|---|---|
| `center` | [타이틀] [에셋] 세로 중앙 정렬. 섹션 타이틀·카드 그리드도 중앙 | 메시지 하나로 끌고 가는 캠페인·이벤트·브랜드 LP, 모바일 비중 높음 |
| `split` | [타이틀] [에셋] 가로 일렬 — 좌 텍스트·CTA / 우 에셋. 섹션 타이틀 좌측 | 설명이 많은 서비스 소개·신청 유도 LP, 데스크톱 비중 높음 (기본값) |

원문이 레퍼런스 이미지를 줬으면 그 정렬을 따른다. 섹션마다 다르게 쓸 수 없다 — 섞으면 validate 가 error.

## 2. 섹션 구성 — 의도 → 프리셋 매핑

| 기획 의도 신호 | preset | 비고 |
|---|---|---|
| 첫 화면 메시지, 서비스 한 줄 정의 | `hero` | 항상 1개, 맨 위 |
| 고객 문제 → 해결, 핵심 가치·혜택 3–4개 | `usp` (bgfullimg) | 기능·화면 설명형이면 `cardType: leading-asset` |
| 타사/기존 방식 비교, 요금제·보장 범위 | `table` | 비교 2열 / 단일 요약 1열 |
| 후기, 사례, 평점 | `review` | 원문에 없으면 예시 + assumptions |
| 이용 방법, 단계, "어떻게" | `process` | 3–5단계. **넘버링 leading 으로만** 구성(에셋 없음). 4단계 이하·짧은 설명 → 카드형, 5단계↑·긴 설명·`layout: list` → 세로 단계 |
| 함께 쓰면 좋은 서비스, 연계 상품 | `cross-sell` | 2–4개 |
| 조건·가격·환불 등 반복 질문 | `faq` | 4개 이상 |
| 상담/신청 폼을 페이지 안에서 받음 | `cta-form` | 외부 신청 플로우로 보내면 생략 |

### 카드 변형 자동 채택 (compile `chooseCardUsage`, 결정적)

아이템을 아래 **형태**로 쓰면 하네스가 카드를 고르고 리포트에 근거를 남긴다. 꼭 지정하려면 섹션에 `card: "..."` (프리셋 허용 목록 안에서만).

| 기획 맥락 | 아이템 형태 | 채택 | 레퍼런스 |
|---|---|---|---|
| 자료실·IR·고객센터 메뉴처럼 **카테고리별 링크 묶음** 2–4개 | `usp`/`cross-sell` · `items[].links[{label, url, actions}]` (actions: download·audio·link·arrow) + `moreHref` | `linkcard` | 주요 투자정보 |
| 혜택·보장 **한 줄 요약** 3–5개 | `usp` · `title ≤14자` + `icon` 만 (body·tag 없음) | `pillcard` | 적금 혜택 필 |
| 금리·요금·수수료·기간별 **조건 표** (비교 아님) | `table` · 카드 1개 · `rows: ["1~3개월: 연 1.8%", …]` 값에 단위 · `rail:false` 로 레일 끔 · `{label,value,highlight}` 로 대표 행 강조 | `kvcard` | 기간별 금리 |
| 절차·안내 **세로 단계** — `process` 는 넘버링, `usp` 안내형은 아이콘(24) + 보조 문장 | `process` 5단계↑ / `layout: "list"` / 긴 보조문 · 또는 `usp` 에 `icon` + `body` | `stepcard` | K-패스 안내 |
| 그 외 | 기존 규칙 | `imgcard · tablecard · listcard …` | |

같은 페이지 안에서 같은 맥락이면 같은 변형을 쓴다 (혜택 필 두 섹션 ✗ → 하나로 합치기).

### 시나리오 기본 스택

| 시나리오 | 스택 | 톤 |
|---|---|---|
| 이사 LP | hero · usp(4) · table · review(4) · process(4) · faq · sticky | 신뢰·안심 |
| 인터넷·렌탈 LP | hero · usp(3) · review(4) · process(4) · cross-sell(3) · faq · sticky | 친근·혜택 명확 |
| 사장님센터 LP | hero · usp(leading-asset) · review(성공사례) · process · cta-form | 전문·신뢰 |
| 빈 LP / 서비스 소개 | hero · usp · process · faq · sticky | 오늘의집 기본 |

규칙
- 정보 흐름: **약속(hero) → 왜(usp/table) → 믿음(review) → 어떻게(process) → 확장(cross-sell) → 남은 의문(faq) → 행동(cta)**.
- 원문에 근거가 없는 섹션은 넣지 않는다 (빈 섹션 < 짧은 페이지).
- 카탈로그에 없는 패턴(예: 영상, 지도, 가격 계산기)이 필요하면 가장 가까운 프리셋으로 대체하고
  `assumptions` 에 "카탈로그 확장 요청 후보: …" 로 남긴다 (PRD §6.3 카탈로그 확장 플로우).
